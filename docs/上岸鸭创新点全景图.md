# 上岸鸭创新点全景图（竞品拆解与 Agent 落地版）

> 依据：用户提供的《上岸鸭竞品拆解与过程干预方案（含大模型技术分析）》第 18–20 页。本文把原文主张、工程支撑和待验证事项分开；不把设计稿或受控模型测试包装成真实用户效果。

## 一、对外主打：只讲清楚两个旗舰创新点

### 创新点 1｜人做、模型验：基于真实作品版本的成果闭环

**一句话：** 不是让模型自己说“做完了”，而是用户提交修改后的 V2，系统拿原判据逐条复核；未通过项才生成下一张行动卡。

**闭环：** 目标与判据 → 作品 V1 → 有证据的位置化诊断 → 微动作行动卡 → 用户修改 → 作品 V2 → 按原判据复核 → 剩余问题再进入下一轮。

**创新价值：**
- 把模型输出从“建议/报告”推进到“真实作品变化是否满足判据”的检查。
- 复核绑定作品版本、原文位置、引文证据和原始判据，降低错版本、无出处或模型自评带来的误放行。
- 只针对剩余差距继续行动，避免每轮都重做整套方案。
- 形成可追溯的证据链：项目 → 判据 → 作品版本/位置 → 诊断版本/差距 → 行动 → 提交 → 复核 → 人工确认。

**演示：** 上传 V1 → 点诊断卡定位原文 → 按行动卡改一处 → 提交 V2 → 逐条显示“通过/未通过/未知” → 未通过项生成下一步。

**验证指标：** 同一批真实材料，对比通用聊天、单 Agent、上岸鸭；统计判据通过数变化、误放行次数、返工轮数、复核耗时。没有真实对照数据前，不宣称效果提升百分比。

### 创新点 2｜知道停在哪，也知道接回哪：按中断原因恢复任务

**一句话：** 用户说“听不进去”和“真的累了”不是同一个状态；系统分别处理理解卡点和精力中断，并回到原任务的准确下一步。

**两条路径：**
- **听不进去：** 保留当前材料、原文位置与任务目标；换成通俗解释/生活类比并标出类比边界；再回到原段落做一个微动作。
- **真的累了：** 保存项目状态、已完成项、未完成项、依赖和存档点；休息后恢复原步骤，必要时只重排剩余任务。

**创新价值：**
- 记忆的是“事情做到哪、下一步是什么”，不只是在聊天记录里堆上下文。
- 根据中断原因路由到不同处理策略，减少用户重新解释背景、重新找位置的成本。
- 把“休息”承诺限定为帮助接续任务，不夸大成保证提高成绩。

**演示：** 在同一任务中分别触发“听不进去”和“真的累了”，检查两条路径是否不同，恢复后是否回到正确项目、原文位置和下一步。

**验证指标：** 中断后重新动手所需时间、重要任务返回率、接续位置准确率、解释后能否复述并完成原动作。

## 二、支撑旗舰创新的六类机制

### 1. 证据绑定的诊断机制
- 输入：目标与判据、指定版本作品、原文、成员能力与历史。
- 输出：差距编号、原文定位、证据引用、具体微动作、未知项。
- 门槛：没有原文位置/引文的诊断不放行；超出上下文预算的材料拆分处理。
- 价值：把“感觉有问题”变成可定位、可复核的问题单。

### 2. 可执行行动卡
- 每一步明确：输入版本、位置、动作、理由、预期变化、产物、自检与失败后的下一步。
- 没有产物或验收条件的步骤不进入日程。
- 价值：把宽泛建议变成用户能在几分钟内开始、完成并交回的动作。

### 3. 按中断类型进行策略路由
- 理解障碍走“换讲法—回原文—完成微动作”。
- 精力中断走“存档—休息—接回原步骤/重排剩余”。
- 价值：同一个按钮背后不是固定回复，而是不同状态对应不同处理流程。

### 4. 跨对话的项目接续
- 新对话中根据用户描述与存档点匹配既有项目。
- 先显示匹配到的项目与准确下一步，再由用户确认后接续。
- 价值：减少跨会话失忆和串项目；确认机制避免自动匹配错项目。

### 5. 有界循环与上下文预算
- 每轮只处理剩余差距，限制循环次数与上下文体量。
- 明确停止条件、失败出口和未知项，不让 Agent 无限自我循环。
- 价值：提升成本可控性、可调试性与失败可解释性。

### 6. 人工确认与风险边界
- 模型的“自评通过”不等于验收；关键结果以新版作品、证据和人工确认作为最终依据。
- 引文不存在、版本不符、证据不足时拒绝放行。
- 对隐私、学术诚信和过度依赖保留风险说明与人工复核。
- 价值：把人放在结果责任链中，而不是把最终决定交给模型自证。

## 三、创新地图：从用户体验到 Agent 工程

| 层面 | 创新主张 | 机制/可观察产物 | 证据状态 |
|---|---|---|---|
| 用户体验 | 不同卡点采用不同恢复路径 | “听不进去/真的累了”两种分流与恢复点 | 设计主张；需真人试点 |
| 任务管理 | 记住任务状态而非只记聊天 | 项目、存档点、依赖、下一步 | 需验证跨会话接续准确率 |
| Agent 协作 | 多角色不是创新本身，关键是交接合同与放行条件 | 诊断、行动、复核各自有输入/输出字段 | 需展示真实链路日志 |
| 模型可靠性 | 证据门、版本门、判据门 | 缺证据/错版本/无产物拒绝放行 | 原文称 PR #22 有相关受控测试；需复核仓库与 CI |
| 评估闭环 | 用户改作品，模型按原判据复核 | V1/V2 对照、剩余差距清单 | 旗舰创新；需要真实材料对照实验 |
| 记忆与上下文 | 基于存档点组装本轮上下文 | 当前材料、原判据、近期失败、存档点 | 需测召回准确率与串项目率 |
| 教育方法 | 示例先行、微动作、明确何时何地做什么 | 示例卡、行动卡、分步撤架 | 理论支撑，不等于产品效果证明 |
| 风险治理 | 不让模型自证成功 | 人工确认、未知状态、隐私/诚信提示 | 需形成测试用例和界面证据 |
| 工程可维护性 | 有界循环与预算限制 | 失败出口、日志、成本/时延统计 | 需运行时数据与告警 |
| 产品差异化 | 从“回答问题”转为“推动真实作品完成并恢复执行” | 可演示的 V1→V2 闭环和中断接续 | 应以同材料竞品对照验证，不宜无证据声称竞品没有 |

## 四、与竞品比较时的表述规则

不要笼统写“所有竞品都做不到”。建议按同一测试任务比较下列可观察行为：
1. 能否引用用户作品中的准确位置；
2. 能否把诊断变成有产物、有验收条件的微动作；
3. 能否对用户提交的新版本按原判据复核；
4. 能否在复核失败后只针对剩余问题继续；
5. 能否区分理解障碍和精力中断，并接回准确步骤；
6. 能否显示证据不足、错版本、未知状态和失败出口。

对比对象、版本、测试输入、成功标准与结果均应留档。公开资料没有证实的竞品能力应标注“未查证”，不能写成“竞品没有”。

## 五、证据状态与开发顺序

### 已有材料支持的描述
- 原文描述了大模型流水线、证据门、微动作门槛、跨对话接续、有界循环与上下文预算。
- 原文称 PR #22 相关 70 项测试通过，同时明确这些测试使用受控模型回复，不代表真实模型效果。
- 原文把“人做、模型验的成果闭环”和“按中断原因恢复任务”列为两项旗舰创新。

### 仍需核实/验证
- PR #21、PR #22 是否存在于当前目标仓库、是否已合并、对应测试是否在 CI 中通过。
- 真实模型在无效引文、错版本、超长输入、重复失败时的表现。
- 真人试点中的判据通过率、误放行、返工次数、接续成功率与重新开始耗时。
- 公网演示链接、匿名测试账号、脱敏样例和端到端日志。

### 建议实施顺序
1. **先核仓库证据：** 定位 PR/分支/提交/CI，区分“文档描述”“代码存在”“运行通过”。
2. **做端到端演示：** 选一份脱敏样例，跑通 V1→定位诊断→行动卡→V2→复核。
3. **做中断接续演示：** 对同一任务触发两种中断，验证路径与恢复位置不同。
4. **做对照测试：** 固定输入、固定判据、记录通用聊天/单 Agent/上岸鸭的结果。
5. **再写效果结论：** 只使用可复核数据，未测项目明确标“待验证”。

## 六、对外 30 秒讲法

上岸鸭不把“模型生成了答案”当成任务完成。第一项创新是“人做、模型验”：用户修改真实作品后，系统拿原判据逐条复核，只把没通过的差距变成下一步。第二项创新是“中断后能接回”：听不懂就换讲法并回到原文，累了就保存状态，之后接回准确步骤。两项创新都能通过作品版本、原文位置、复核结果和接续记录进行验证；真实效果以试点数据为准。
